# luckyxiang-productintel

> 产品官网深度情报采集：从 URL 到结构化报告，系统化、可追溯、零幻觉。

## 概述

luckyxiang-productintel 帮助用户系统化采集产品官网信息并生成结构化竞品分析报告。核心特色：自动发现站点导航结构 → 双通道采集（WebFetch 优先 + WebSearch 回退）→ 中间数据可追溯 → 标准 10 节报告框架 → HTML 左侧导航栏。

来自 Skydio 竞品分析实战经验，解决"官网信息分散、采集效率低、数据不可追溯"的痛点。

## 快速参考

| 命令 | 说明 |
|------|------|
| `/productintel` | 交互式采集（逐步确认采集计划） |
| `/productintel "Skydio https://skydio.com"` | 带公司名和 URL 直接采集 |
| `/productintel "DJI" --industry drone` | 指定行业，启用行业适配 |
| `/productintel "Palantir" --focus platform` | 聚焦特定类型（platform/software/hardware） |
| `/productintel "公司名" --extra-pages "/pricing,/careers"` | 追加额外页面 |
| `/productintel "公司名" --scan-only` | 只扫描站点结构，不采集内容 |

## 示例

```bash
# 交互式采集
/productintel

# 直接指定公司
/productintel "Skydio https://www.skydio.com"

# 指定行业 + 聚焦
/productintel "DJI https://www.dji.com" --industry drone --focus hardware

# 追加深层页面
/productintel "Palantir https://www.palantir.com" --extra-pages "/foundry,/gotham,/apollo"

# 只扫描站点结构，不采集内容
/productintel "Palantir https://www.palantir.com" --scan-only
```

## 工作流

```
步骤0: 站点发现 → 步骤0.5: 站点扫描 → 步骤1: 逐页采集 → 步骤2: 数据补充 → 步骤3: MD报告 → 步骤3.5: 内容核对 → 步骤4: HTML报告 → 步骤5: 质量检查
```

### 步骤 0：站点发现

**目标**：确定要采集的页面列表，展示计划等待用户确认。

1. 用 WebFetch 获取首页内容（WebSearch 仅限 `site:{domain}` 查询）
2. 从首页导航栏提取产品/软件/平台/解决方案等关键链接
3. 按类型分类整理页面列表：

| 类型 | 典型路径模式 | 优先级 |
|------|-------------|--------|
| 产品页 | `/products/*`, `/x10`, `/r10` | 最高 |
| 软件页 | `/software/*`, `/apps/*` | 高 |
| 平台页 | `/platform/*`, `/technology/*` | 高 |
| 解决方案 | `/solutions/*`, `/industries/*` | 中 |
| 客户/案例 | `/customers/*`, `/case-studies/*` | 中 |
| 开发者 | `/developer*`, `/api/*` | 中 |
| 关于公司 | `/about`, `/company` | 低 |

4. 展示采集计划表格（URL、类型、预估内容），等待用户确认或补充
5. 用户可通过 `--extra-pages` 参数追加页面

**输出**：确认后的页面种子列表（作为步骤0.5站点扫描的输入种子）

> 步骤0的输出将作为步骤0.5站点扫描的种子URL，站点扫描会在此基础上通过 sitemap/robots.txt/首页深度提取等方式扩展发现更多页面。

### 步骤 0.5：站点扫描

**目标**：全量扫描官网页面结构，分类标注优先级，生成可选择的采集计划。默认只采集高优先级页面。

**输入**：步骤0发现的首页导航链接 + 用户提供的 URL

#### 扫描策略（按优先级尝试）

```
对目标站点：
  1. 尝试获取 {domain}/sitemap.xml → 解析所有 <loc> URL
  2. 如果 sitemap 不可用 → 读取 {domain}/robots.txt，提取 Sitemap 指令并获取
  3. 从首页 HTML 中提取所有 <a href> 内链（补充步骤0的导航栏提取）
  4. 对已发现的目录级页面，推测常见子路径（如 /platforms/ → /platforms/aip/, /platforms/foundry/ 等）
```

#### 分类与优先级算法

对每个发现的 URL，基于路径模式自动分类和定优先级：

| 优先级 | 分类 | 路径模式 | 说明 |
|--------|------|---------|------|
| 🔴 P0 | 核心产品/平台 | `/platforms/*`, `/products/*`, `/product/*`（一二级页面） | 产品/平台的核心描述页 |
| 🔴 P0 | 定价/计划 | `*/plans/*`, `*/pricing/*`, `*/pricing` | 可能包含定价信息 |
| 🔴 P0 | 核心技术 | `*/ontology/*`, `*/ai*`, `*/architecture*` | 核心技术/架构页面 |
| 🟠 P1 | 行业解决方案 | `/offerings/*`, `/solutions/*`, `/industries/*` | 行业/垂直方案 |
| 🟠 P1 | 国防/政府 | `*/defense/*`, `*/government/*`, `*/federal*` | 政府/国防方案 |
| 🟠 P1 | 客户/案例 | `/customers/*`, `/impact/*`, `/case-studies/*` | 客户案例 |
| 🟠 P1 | 核心能力子页 | `*/digital-twin*`, `*/streaming*`, `*/marketplace*`, `*/bootcamp*`, `*/agentcamp*` | 平台能力子页面 |
| 🟡 P2 | 合作伙伴 | `/partnerships/*`, `/partners/*` | 合作生态 |
| 🟡 P2 | 开发者 | `/developers/*`, `/developer*`, `/api/*`, `*/sdk*` | 开发者资源 |
| 🟡 P2 | 公司信息 | `/about*`, `/careers*`, `/newsroom*`, `/blog*` | 公司/招聘/新闻 |
| 🟡 P2 | 合规/安全 | `*/security*`, `*/privacy*`, `*/compliance*`, `*/trust*` | 安全合规 |
| ⚪ P3 | 其他 | 不匹配以上模式 | 静态页/重定向/低价值 |

#### 去重规则

- 去除 URL trailing slash 差异（`/about/` = `/about`）
- 去除 locale/语言前缀的同源页面（如 `/en/about` 和 `/about` 只保留一个）
- 去除分页参数（`?page=2`）
- 去除 hash-only 链接（`#section`）
- 去除文件扩展名（`.pdf`, `.jpg`, `.png`, `.xml` 等非页面资源）
- 保留不同路径的页面，即使内容可能重叠

```markdown
| 🔴 P0 高优先级 | {n0} |
| 🟠 P1 中优先级 | {n1} |
| 🟡 P2 低优先级 | {n2} |
| ⚪ P3 其他 | {n3} |

## 🔴 P0 高优先级页面（{n0}个）— 默认采集

| # | 路径 | 分类 | 推测内容 |
|---|------|------|---------|

| # | 路径 | 分类 | 推测内容 |

| # | 路径 | 说明 |

- **默认采集**：P0 全部（{n0}个页面）
- **推荐扩展**：P1 中与目标行业相关的页面

```

#### 用户交互

扫描完成后，向用户展示摘要并询问采集范围：

```
站点扫描完成：发现 {M} 个页面

```

**输出**：确认后的按优先级排序的采集计划 + 站点扫描报告文件

### 步骤 1：逐页采集

**目标**：逐页采集内容，保存中间数据文件。

> **输入变更**：步骤1的输入为步骤0.5站点扫描确认后的采集计划（按优先级排序），而非步骤0的原始导航链接。开始采集前，展示实际将采集的页面数量和预估时间。

**采集策略**（单站点）：

> ⚠️ **核心原则：所有数据只从目标站点获取，禁止从第三方网站搜索补充。** WebSearch 仅限 `site:目标域名` 查询，不得搜索其他来源。这确保报告内容100%来自官网，杜绝外部信息混入导致的准确性问题。

```
对每个页面：
  1. 先尝试 WebFetch(url)
  2. 如果 WebFetch 被阻止或返回空 → 用 WebSearch("site:{domain} {page-topic}")
  3. 如果 WebSearch 也无结果 → 标记为"采集失败"，记录原因
  4. ❌ 禁止：WebSearch 不带 site: 限定、搜索第三方网站、引用非官网来源
```

**SPA/动态渲染页面处理**：

> ⚠️ 许多现代网站（Next.js、React SPA 等）的内容不在初始 HTML 或 `__NEXT_DATA__` 中，而是通过客户端 JavaScript 动态渲染。WebFetch 和 curl 只能获取初始 HTML，可能只拿到空壳页面（meta description + 占位符）。

```
检测 SPA 空壳页面：
  1. 如果 WebFetch/curl 返回的内容只有 meta description 和少量占位文本（如"Placeholder for Video"）
  2. 且页面标题与描述暗示应有丰富内容（如产品详情页）
  3. → 判定为"SPA 动态渲染页面"，进入自动渲染流程

自动渲染流程（按优先级尝试）：
  1. curl 获取 HTML → 提取 __NEXT_DATA__ JSON → 深度搜索所有嵌套内容
  2. 如果 __NEXT_DATA__ 也为空壳 → 尝试 _next/data/{buildId}/{slug}.json 端点
  3. 如果仍为空壳 → 自动调用本地浏览器 headless 模式渲染：
     a. 优先 Edge（Windows 自带）：msedge.exe --headless=new --dump-dom {url}
     b. 备选 Firefox：无 --dump-dom，需 Playwright/Selenium
     d. 提取渲染后 HTML → 去除 script/style 标签 → 提取纯文本
     e. Method 标注为 "Headless browser dump-dom (SPA dynamic content)"
  4. 如果本地浏览器不可用 → 提示用户手动导出（最后手段）

Headless 浏览器渲染脚本（Python）：
  import subprocess, re
  result = subprocess.run([
      r'C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe',
      '--headless=new', '--disable-gpu', '--no-sandbox',
      '--dump-dom', '--virtual-time-budget=10000',
      url
  ], capture_output=True, timeout=60)
  html = result.stdout.decode('utf-8', errors='replace')
  clean = re.sub(r'<script[^>]*>.*?</script>', '', html, flags=re.DOTALL)
  clean = re.sub(r'<style[^>]*>.*?</style>', '', clean, flags=re.DOTALL)
  clean = re.sub(r'<[^>]+>', ' ', clean)
  clean = re.sub(r'\s+', ' ', clean).strip()
```

**用户手动导出（最后手段）**：

仅在本地浏览器不可用时，提示用户在浏览器 Console 执行：

```js
(() => {
  const text = document.body.innerText;
  const blob = new Blob([text], {type: 'text/plain'});
  const a = document.createElement('a');
  a.href = URL.createObjectURL(blob);
  a.download = '{page-slug}_rendered.txt';
  a.click();
})()
```

**限流策略**：

| 场景 | 处理 |
|------|------|
| 正常请求 | 每次请求间隔 ≥ 3 秒 |
| 429 限流 | 等待 30 秒后重试，最多 2 次 |
| 连续 3 次失败 | 跳过该页面，标记原因 |

**中间数据格式**：

文件名：`{序号:02d}-{页面简称}.md`，保存在 `{输出目录}/官网/` 下。

```markdown
# {页面标题} Raw Data
- URL: {完整URL}
- Fetched: {采集日期 YYYY-MM-DD}
- Method: {WebFetch | WebSearch | WebSearch+webReader | curl+NEXT_DATA | Headless browser dump-dom | Browser manual export}
- Status: {成功 | 部分成功 | 失败}

## Tagline
{页面标语/口号}

## Description
{页面描述}

## {按页面实际内容组织}
...
```

**数据缺口标注**：采集过程中发现的信息缺口用 `⚠️ 数据缺口：{描述}` 标记。

### 步骤 2：数据补充

**目标**：识别并补充步骤1中遗漏的关键信息。

> ⚠️ **核心原则：所有补充数据只从目标站点获取，禁止从第三方网站搜索。** 如果官网未公开某项信息，直接标注为"❌ 缺失"或"⚠️ 官网未公开"，绝不从外部来源补充。

1. 检查采集数据是否覆盖以下必填项：

| 必填信息 | 来源 | 补充方式 |
|---------|------|---------|
| 公司基础信息 | 首页/About页 | 从目标站点其他页面补充 |
| 产品核心规格 | 产品页 | 标注为"官网未公开" |
| 客户/案例 | 客户页 | 从目标站点 Impact 页补充 |
| 合作伙伴 | 集成页 | 从目标站点 Partnerships 页补充 |
| 定价信息 | 定价页 | 标注为"官网未公开" |

2. 补充方式仅限：从目标站点其他已采集页面中提取相关信息
3. 如果目标站点确实没有某项信息 → 标注"❌ 缺失"，不编造、不外搜
4. 补充数据保存为额外中间文件（如 `99-supplementary.md`）
5. 所有数据必须标注来源页面URL，无法验证的标注为"⚠️ 待验证"

### 步骤 3：MD 报告生成

**目标**：生成结构化 MD 竞品分析报告。

**标准 10 节框架**：

| # | 章节 | 内容 | 必选 |
|---|------|------|------|
| 1 | 公司概况 | 名称、成立时间、总部、定位、制造、关键数据 | 是 |
| 2 | 产品线总览 | 产品架构图/表，分层分类展示 | 是 |
| 3 | 各产品详细能力 | 每个产品独立子节：规格、传感器/功能、AI能力、连接、附件、安全 | 是 |
| 4 | 软件生态详细能力 | 每个软件产品独立子节：定位、核心功能、应用场景、集成 | 按类型 |
| 5 | 核心平台能力 | 每个平台独立子节：技术架构、核心模块、设计理念 | 按类型 |
| 6 | 解决方案 | 按场景描述核心价值、子场景 | 是 |
| 7 | 行业客户与生态 | 覆盖行业、知名客户、案例摘要、合作伙伴 | 是 |
| 8 | 核心价值 | 提炼 5-8 条核心价值主张 | 是 |
| 9 | 其他关注点 | 制造/供应链、法规合规、市场数据、路线图、海外市场 | 是 |
| 10 | 数据可靠性 | 每项数据标注可靠性等级 | 是 |

**行业适配**：

| 行业类型 | 章节侧重调整 |
|---------|-------------|
| 硬件产品（无人机/机器人/设备） | 强化第3节规格表、传感器、附件生态 |
| 软件产品（SaaS/平台） | 强化第4节功能矩阵、定价模式、API生态 |
| 软硬一体 | 第3-5节均衡展开，强调端到端集成 |
| 服务/咨询 | 强化第6节解决方案、第7节客户案例 |

**数据可靠性标注**：

| 标注 | 含义 | 使用场景 |
|------|------|---------|
| ✅ 高 | 直接来自官网产品页 | 官方规格、功能描述 |
| ⚠️ 中 | 来自博客/发布会/第三方 | 预发布产品规格、市场数据 |
| ❌ 缺失 | 官网未公开 | 定价、未发布产品详细参数 |

**产品功能描述要求**：
- 每个产品/软件/平台必须有详细功能描述，不能只有参数表
- 包含具体应用场景和案例（如"800英尺外读取车牌"）
- 功能描述要回答"能做什么"和"在什么场景下用"
- 不用担心内容长度，详细优于简洁

### 步骤 3.5：内容核对

**目标**：将 MD 报告中的每一项事实性声明与原始采集数据进行逐条核对，删除或修正任何无源可查的捏造内容。

> ⚠️ **这是防止 AI 幻觉/捏造的关键防线。** LLM 在生成报告时可能"合理推测"或"补充"官网未提及的信息。步骤3.5 通过反向核对确保报告中每一句话都有据可查。

**核对流程**：

```
对 MD 报告中的每个产品/平台/能力章节：
  1. 提取该章节中所有事实性声明（数据、规格、金额、日期、功能描述、技术架构等）
  2. 对每个声明，在步骤1的中间数据文件中查找对应原文
  3. 判定结果：
     ✅ 有据可查 → 保留，标注来源页面
     ⚠️ 间接推断 → 保留但标注"⚠️ 基于官网描述推断"
     ❌ 无源可查 → 删除或改写为"官网未公开"
```

**核对清单**（每项必须逐一检查）：

| # | 核对项 | 检查方式 |
|---|--------|---------|
| 1 | 产品/功能名称 | 在中间数据中搜索精确名称，确认官网确有此名称 |
| 2 | 数据/金额/日期 | 逐条与中间数据比对，不一致则删除 |
| 3 | 技术架构描述 | 确认架构图/层级在中间数据中有对应描述 |
| 4 | 功能描述的具体场景 | 确认场景描述来自官网，而非AI推测 |
| 5 | 客户名称和案例 | 确认客户名在官网 Impact/Customers 页出现 |
| 6 | 合作伙伴名称 | 确认合作伙伴在官网 Partnerships 页出现 |
| 7 | 竞争优势/价值主张 | 确认措辞来自官网文案，非AI加工 |
| 8 | 产品间关系描述 | 确认平台间的集成关系在官网有明确提及 |

**核对结果输出**：

在 MD 报告末尾添加核对摘要：

```markdown
## 内容核对摘要

> 核对日期：YYYY-MM-DD | 核对范围：全报告

| 章节 | 核对项数 | ✅ 有据 | ⚠️ 推断 | ❌ 已删除 |
|------|---------|--------|---------|----------|
| 3.1 AIP | {n} | {n} | {n} | {n} |
| ... | ... | ... | ... | ... |
```

**如果发现捏造内容**：
1. 立即删除该内容，替换为"⚠️ 官网未公开"
2. 在核对摘要中记录删除项
3. 如果整节内容都无据可查，保留节标题但标注"⚠️ 该产品/能力在官网无详细描述"

### 步骤 4：HTML 报告生成（分段写入）

**目标**：生成带左侧导航栏的 HTML 报告，按章节分段写入，避免一次性写入失败。

> ⚠️ **核心原则：分段写入，逐章追加，进度可见。** HTML 报告内容量大（通常数千行），一次性写入容易因 token 限制或写入超时导致失败。改为分段写入：先写骨架，再逐章节追加，每段展示进度。

#### 阶段 4.0：写入计划展示

1. 根据步骤3的 MD 报告章节结构，生成写入计划表
2. 向用户展示计划，包含：章节名、预估内容量、写入顺序
3. 等待用户确认后开始写入

**写入计划模板**：

```markdown
## HTML 写入计划

| # | 章节 | 预估内容量 | 写入方式 | 状态 |
|---|------|----------|---------|------|
| 0 | HTML 骨架（CSS+JS+导航） | ~500行 | Write | ⏳ |
| 1 | 报告头部（header） | ~20行 | 骨架内含 | ⏳ |
| 2 | 一、公司概况 | ~50行 | Edit追加 | ⏳ |
| 3 | 二、产品线总览 | ~100行 | Edit追加 | ⏳ |
| 4 | 三、各产品详细能力 | ~200行 | Edit追加 | ⏳ |
| ... | ... | ... | ... | ... |
| N | 十、数据可靠性 | ~30行 | Edit追加 | ⏳ |
| N+1 | 关闭标签 + JS脚本 | ~60行 | Edit追加 | ⏳ |

预计总写入次数：{N+2}次
```

#### 阶段 4.1：写入 HTML 骨架文件

1. 读取 `references/html-style.md` 获取完整 CSS/JS/HTML 骨架
2. 替换 `{{COMPANY_NAME}}` 占位符
3. 根据报告章节动态生成 `{{NAV_ITEMS}}`（导航项）
4. 写入骨架文件：包含完整的 `<head>`、CSS、`<nav>`、汉堡菜单按钮、遮罩层
   - `{{MAIN_CONTENT}}` 区域写入报告头部（header 区域）
   - 在 header 之后放置 `<!-- SECTION_INSERT_POINT -->` 标记点
5. 确认骨架写入成功，展示进度：`✅ 骨架写入完成`

#### 阶段 4.2~4.N：逐章节追加内容

对每个章节（按写入计划顺序）：

1. 将该章节的 MD 内容转为 HTML
2. 使用 **Edit 工具**追加到骨架文件：
   - `old_string` = `<!-- SECTION_INSERT_POINT -->`
   - `new_string` = 章节 HTML 内容 + `<!-- SECTION_INSERT_POINT -->`
   - 标记点始终保持在最后，确保下次追加位置正确
3. 每个章节用 `<div class="section" id="secN">` 包裹
4. 章节内使用对应组件：
   - 产品线总览 → `product-card` 组件（按分类分组）
   - 产品详细 → `metrics` + `table` + `sensor-card` 组件
   - 其他章节 → `section` + `highlight` + `table`
5. 确认写入成功后，展示进度：

```
✅ 第1章「公司概况」写入完成
✅ 第2章「产品线总览」写入完成
进度：2/10 章节完成 (20%)
```

6. 如果某个章节内容特别长（如产品详细能力节含多个子产品），可进一步拆分为子节追加：
   - 每个 h3 子产品独立一次 Edit 追加
   - 避免单次追加内容过多

#### 阶段 4.N+1：写入尾部 + 关闭标签

1. 写入最后一个内容章节（数据可靠性）
2. 替换 `<!-- SECTION_INSERT_POINT -->` 为空（移除标记点）
3. 确认 `</div>` (container) 和 `</main>` 关闭标签正确
4. 确认 `<script>` 部分（IntersectionObserver + 汉堡菜单）完整
5. 展示最终进度：`✅ HTML 报告生成完成，共 {N} 章节`

#### 失败恢复机制

如果某章节写入失败：

1. **不继续下一章节**，避免内容错位
2. 向用户报告失败章节和错误信息
3. 用户可选择：
   - **重试**：重新生成该章节 HTML 并追加
   - **跳过**：标记为 `⚠️ 生成失败`，继续下一章节
   - **终止**：保留已写入部分，手动补全

#### 导航项生成规则

导航栏使用三层结构，**必须严格遵循层级关系**：

| 层级 | CSS 类 | 作用 | 示例 |
|------|--------|------|------|
| 顶级章节 | `nav-item` | 一级章节，可点击跳转 | "三、各产品详细能力" |
| 分组标签 | `nav-category` | 不可点击的分类标签，用于归类子章节 | "硬件产品" |
| 子章节 | `nav-sub-item` | 二级章节，可点击跳转，必须挂在 `nav-category` 之后 | "AuterionOS"、"Skynode" |

**规则**：

1. **`nav-item` 是顶级章节**，对应报告的"一、二、三..."大章节，**永远不要放在 `nav-category` 下面**
2. **`nav-category` 是分组标签**，不可点击，仅用于在某个 `nav-item` 下方归类其子章节
3. **`nav-sub-item` 是子章节**，可点击跳转，**必须紧跟在某个 `nav-category` 之后**，表示属于该分组
4. 标准层级模式为：
   ```
   nav-item（顶级章节）
   nav-category（分组标签）
   nav-sub-item（子章节1）
   nav-sub-item（子章节2）
   nav-item（下一个顶级章节）
   ```
5. 固定顶级章节：公司概况、产品线总览、核心价值、数据可靠性
6. 含子章节的顶级章节：各产品详细能力、软件生态详细能力、核心平台能力、解决方案
7. 每个 `nav-sub-item` 的 `data-target` 必须对应 HTML 内容中某个 `id` 属性值

## 能力边界

**做一件事**：从产品官网系统化采集信息并生成结构化分析报告。

| 输入 | 处理方式 |
|------|---------|
| 公司名 + 官网 URL | 完整采集流程 |
| 公司名（无 URL） | WebSearch 查找官网后执行 |
| --industry 参数 | 启用行业适配报告框架 |
| --focus 参数 | 聚焦特定产品类型，深入采集 |
| --extra-pages 参数 | 追加用户指定的额外页面 |
| --scan-only 参数 | 只执行步骤0+0.5，输出扫描报告后停止 |

**USE FOR**：
- 官网采集、产品情报、竞品官网分析、site recon、product intel
- 帮我从官网收集信息、采集官网数据、系统化分析官网
- 竞品官网调研、产品官网深度采集、网站信息提取

**DO NOT USE FOR**：
- 纯竞品横向对比（用 hv-analysis）
- 多源文档综合分析（用 deepreport）
- 单文档摘要（用 docsummer）
- 通俗解读（用 plainreport）
- 知识图谱生成（用 graphify）

**独立性声明**：完全独立运行，不依赖其他 Skill。输出数据可被 hv-analysis、deepreport 等后续消费。

## 异常处理

| 场景 | 处理 |
|------|------|
| WebFetch 被阻止 | 自动切换 WebSearch("site:{domain} ...")，记录采集方法 |
| 429 限流 | 等待 30 秒重试，最多 2 次 |
| WebSearch 返回空 | 换用不同 site: 搜索词重试 1 次，仍无结果则标注"采集失败" |
| 产品规格官网未公开 | 标注"未公开"，不编造 |
| 定价信息缺失 | 在数据可靠性表标注"❌ 缺失" |
| 非中英文网站 | 尝试采集，标注语言，关键信息翻译 |
| 网站结构异常（SPA/动态加载） | 按"SPA/动态渲染页面处理"流程：先尝试 __NEXT_DATA__ 和 _next/data 端点，仍为空壳则提示用户从浏览器导出渲染后文本 |
| 公司无独立产品页 | 按实际页面结构调整报告框架 |
| 输出目录已存在 | 追加采集，不覆盖已有文件（除非用户确认） |
| sitemap.xml 不存在或无法访问 | 回退到 robots.txt + 首页链接提取，标注"sitemap不可用" |
| sitemap.xml 过大（>5000 URL） | 采样前2000个URL + 按目录去重，标注"sitemap过大已采样" |
| 扫描发现大量重复/国际化页面 | 自动去重（保留主语言版本），标注去重数量 |

## 与其他 Skill 的关系

```
website-recon (深度官网采集)
    ↓ 输出: 中间数据 + MD/HTML 报告
hv-analysis (横纵分析/竞品研究)
    ↓ 可消费 productintel 的数据作为纵轴素材
deepreport (多源深度分析)
    ↓ 可将 productintel 的 MD 报告作为输入源之一
```

- **productintel → hv-analysis**：productintel 的输出可作为 hv-analysis 纵轴（公司发展历程）的数据源
- **productintel → deepreport**：productintel 的 MD 报告可作为 deepreport 的多源输入之一
- **不互相替代**：productintel 只做官网采集，不做竞品横向对比或多源综合
