# 提取、类比映射与验证 Prompt 模板

## 素材提取 Prompt（步骤 1a：初稿）

```xml
<role>
你是一个精确信息提取引擎。从文档中提取关键信息，不做评价、不添加背景知识、不推断。
</role>

<constraints>
C1. 忠实约束：所有内容必须源自文档原文。绝不添加原文没有的信息。
C2. 精确约束：数据（数字、比例、日期、名称）必须与原文完全一致。
C3. 不确定约束：原文模糊或矛盾处，标注 [原文表述不清]，而非自行解释。
</constraints>

<task>
从以下文档中提取：
1. 核心主题（一句话）
2. 关键数据点（5-15个，精确数值，标注原文位置）
3. 核心结论（3-5条）
4. 关键术语定义（3-10个）
5. 因果关系（2-5条）
6. 与其他工作的关系/引用
7. 可视化素材建议（适合画什么图）
</task>

<content>
{document_content}
</content>
```

## 密度增强 Prompt（步骤 1b：1-2轮）

```xml
<role>
你正在进行信息密度增强。对比当前提取结果与原文，识别遗漏的关键实体。
</role>

<task>
1. 读取 <extract> 中的当前提取结果
2. 读取 <source> 中的原文
3. 识别遗漏的关键实体（Relevant + Specific + Novel + Faithful）
4. 列出遗漏实体（最多 5 个），格式：[ENTITY: 内容 | 类型: 数据/结论/因果/定义]
5. 融入遗漏实体，保持总长度不超过 600 字
6. 如果已无重要遗漏，输出 "DENSITY_COMPLETE"
</task>

<extract>
{current_extraction}
</extract>

<source>
{document_content}
</source>
```

终止条件：输出 `DENSITY_COMPLETE` 或已执行 2 轮。

## 类比映射 Prompt（步骤 2：核心差异化步骤）

```xml
<role>
你是一个类比生成引擎。你的职责是将技术概念转化为日常生活中的类比，让非技术读者也能理解。
</role>

<constraints>
C1. 类比必须来自日常生活经验（开车、做饭、公司管理、微信群、快递、学校、医院、超市等）
C2. 类比的结构必须与技术概念的结构对应（输入→处理→输出的映射）
C3. 每个类比必须说明"类比在哪里失效"——技术概念的哪个方面无法用这个类比解释
C4. 同一报告中的类比应尽量来自同一个"生活场景"（如都用"公司管理"类比），保持一致性
C5. 类比不能歪曲技术事实——类比中的因果关系必须与技术概念中的因果关系一致
</constraints>

<task>
从以下素材卡片中提取所有核心技术概念，为每个概念生成：

1. 概念名称
2. 日常类比（2-3句话，用"就像..."开头）
3. 映射点（类比中的X = 技术中的Y，列出3-5个对应关系）
4. 类比失效点（这个类比无法解释什么）
5. 推荐的类比场景标签（如"公司管理"、"交通系统"、"厨房"等）
</task>

<output_format>
对每个概念输出：

### 类比卡片：{概念名}

- **概念**：{技术概念名称}
- **日常类比**：{2-3句话，用"就像..."开头}
- **映射点**：
  - 类比中的 A = 技术中的 X
  - 类比中的 B = 技术中的 Y
  - ...
- **类比失效点**：{这个类比无法解释什么}
- **场景标签**：{如"公司管理"、"交通系统"、"厨房"}
</output_format>

<material_cards>
{all_material_cards}
</material_cards>
```

## 事实验证 Prompt（步骤 4：不可跳过）

```xml
<role>
你正在进行事实验证。检查报告内容中的每个关键声明是否与源文件一致。
</role>

<task>
1. 从 <chapter> 中提取所有关键声明（包含数据、结论、因果关系的句子）
2. 对每个声明生成验证问题："源文件是否确实说了 [具体声明内容]？"
3. 回到 <sources> 中的素材卡片和原文查找答案
4. 分类：
   - VERIFIED：源文件明确支持 → 保留
   - PARTIALLY_VERIFIED：源文件部分支持 → 修正为与原文一致的版本
   - UNVERIFIED：源文件中找不到 → 删除
   - CONTRADICTED：与源文件矛盾 → 删除
5. 额外验证：检查类比中的因果关系是否与原文中的因果关系一致，如果类比歪曲了事实，修正类比
6. 输出修正后的章节内容（不输出验证过程）
</task>

<chapter>
{chapter_content}
</chapter>

<sources>
{material_cards_and_original_excerpts}
</sources>
```

## 类比优先内容约束（步骤 3）

```xml
<constraints>
C1. 每个核心概念必须先用类比解释，再给精确定义。类比在前，定义在后。
C2. 所有类比使用 .analogy 样式块（💡 通俗理解：...）
C3. 关键要点使用 .key-point 样式块（🔑 关键要点：...）
C4. 不使用代码片段、API参考、命令行示例
C5. 不使用数学公式。如需解释算法，用流程类比代替公式
C6. 技术术语首次出现时用括号附日常解释，如：EKF2（扩展卡尔曼滤波器，就像一个"数据整合大师"）
C7. 语气口语化，像在跟朋友聊天解释，不像在写论文
C8. 每个事实声明必须能追溯到某个源文件的素材卡片
C9. 如果某个章节素材不足，标注 [素材不足，以下内容基于有限信息] 而非编造
</constraints>
```

## 内容生成强制约束（步骤 3 执行时必须遵守）

以下规则在步骤 3 内容生成时**逐条强制执行**，违反任何一条即视为输出不合格：

### HTML 结构约束

1. **CSS 原样粘贴**：从 `references/html-style.md` 复制完整 CSS，粘贴到 `<style>` 标签。禁止修改任何值、禁止新增类名、禁止省略规则。
2. **JS 原样粘贴**：从 `references/html-style.md` 复制完整 JS，粘贴到 `<script>` 标签。禁止修改。
3. **9 节固定**：恰好 9 个 `<div class="section" id="sN">`，id 从 s1 到 s9。禁止增减。
4. **组件必含**：每节必须包含 `section-schema.md` 中规定的必含组件。缺少任何组件即不合格。

### 样式约束

5. **禁止自创类名**：只能使用 `html-style.md` 中定义的 CSS 类名（`.analogy`、`.key-point`、`.stat-row`、`.stat-box`、`.card-grid`、`.card`、`.table-wrap`、`.svg-wrap`、`.svg-caption`、`.example-box`、`.step`、`.step-num`、`.step-text`、`.pros-cons`、`.con`、`.pro`、`.scenario-grid`、`.scenario-card`、`.icon`、`.subsection`、`.subsection-title`、`.hero`、`.tagline`、`.subtitle`、`.footer`、`.nav`、`.main`、`.section`、`.section-title`、`.section-num`、`.tag`、`.tag-blue`、`.tag-green`、`.tag-purple`、`.tag-orange`、`.tag-red`、`.tag-teal`）。禁止新增任何类名。
6. **禁止深色主题**：`--bg` 必须为 `#fafbfc`，`--bg2` 必须为 `#ffffff`，`--text` 必须为 `#1a202c`。禁止改为深色值。
7. **SVG 配色一致**：所有 SVG 使用 `svg-guide.md` 定义的 6 色强调色系 + 浅色填充 + 深色描边。

### 内容约束

8. **类比在前定义在后**：每个核心技术概念先用 `.analogy` 块给日常类比，再给精确定义。
9. **类比一致性**：同一报告中的类比尽量来自同一个生活场景。
10. **零幻觉**：只写素材中有的内容，不确定的标注 `[原文未提及]`。
11. **口语化**：像跟朋友聊天解释，不用代码片段、不用数学公式。

### 自检流程

生成完整 HTML 后、写入文件前，必须执行以下自检：

```
自检项目：
□ CSS 与 html-style.md 完全一致？
□ JS 与 html-style.md 完全一致？
□ 恰好 9 个 section（s1-s9）？
□ 每节包含规定的必含组件？
□ 无自创 CSS 类名？
□ 无深色主题元素？
□ 所有 SVG 浅色填充 + 深色描边？
□ 导航栏包含 9 节链接？

任何一项不通过 → 修正后再输出
```
