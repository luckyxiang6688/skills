# luckyxiang-plainreport

> 多源素材 → 通俗易懂解读（HTML），用日常类比替代技术术语，用问答结构替代学术框架。独立运行，内容零幻觉。

## 概述

luckyxiang-plainreport 将多种源素材（论文、文档、代码、数据、知识图谱分析等）自动转化为面向非技术受众的通俗解读 HTML。核心特色：每个技术概念先给日常类比再给定义；固定 9 节问答式结构；浅色主题 + 左侧固定导航栏 + 解释性 SVG 图表；6 步工作流含不可跳过的事实验证步骤，确保内容零幻觉；完全独立运行，不依赖其他 skill。

## 快速参考

| 命令 | 说明 |
|------|------|
| `/plainreport <路径>` | 完整通俗解读 |
| `/plainreport <路径> --topic "主题"` | 指定解读主题 |
| `/plainreport <路径> --output report.html` | 指定输出路径 |
| `/plainreport <路径> --auto` | 跳过确认，直接生成 |

## 示例

```bash
# 解读一组 PDF 论文
/plainreport D:\work\claude\7部\CNN\*.pdf

# 指定主题
/plainreport D:\work\claude\7部\PX4\ --topic "PX4 无人机飞控系统通俗解读"

# 解读代码项目
/plainreport src/**/*.ts --topic "项目架构通俗解读"

# 混合素材 + 指定输出
/plainreport data/*.json,docs/*.md --output 解读.html

# 自动模式（跳过确认）
/plainreport D:\work\claude\7部\CNN\ --auto
```

## 能力边界

这个 skill 做一件事：**多种源素材 → 通俗易懂的解读 HTML**。

| 输入类型 | 处理方式 |
|---------|---------|
| `.pdf` | Read 工具分页读取（每次最多 20 页） |
| `.md` | Read 工具直接读取 |
| `.doc` / `.docx` | Read 工具直接读取 |
| `.py` / `.js` / `.ts` / `.java` 等 | Read + 结构分析（提取类、函数、模块关系） |
| `.json` / `.yaml` / `.csv` | Read + 结构化数据解析 |
| `.html`（已有分析报告） | Read + 内容提取（复用已有分析） |
| 目录路径 | 递归扫描所有可处理文件 |

**完全独立**，不依赖 deepreport、docsummer、mdtohtml 等任何外部 skill。

## 工作流总览

```
步骤0: 输入解析 → 识别素材类型与数量，确定解读主题
步骤1: 素材提取 → 对每个源文件精确提取关键信息（DRAFT + DENSITY）
步骤2: 类比映射 → 为每个核心技术概念生成日常类比（类比优先策略的核心步骤）
步骤3: 内容生成 → 按固定9节问答结构生成内容 + SVG 图表（类比在前，定义在后）
步骤4: 事实验证 → 逐章回源文件核实，删除/标注无法验证的内容（不可跳过）
步骤5: 组装输出 → 单文件 HTML（浅色主题 + 问答结构 + 解释性 SVG + 类比卡片）
```

## 步骤 0：输入解析

从用户命令中提取：

1. **源材料路径**（必填）：支持 glob 模式和逗号分隔多路径
2. **解读主题**（可选，`--topic`）：默认从素材内容推断
3. **输出路径**（可选，`--output`）：默认源目录下 `<主题>-通俗解读.html`
4. **自动模式**（可选，`--auto`）：跳过确认，直接生成

### 文件扫描

- 如果输入是目录，递归扫描所有可处理文件
- 如果输入是 glob 模式（如 `*.pdf`），用 Glob 工具匹配
- 如果输入是逗号分隔的多路径，逐个处理
- 忽略不可处理的文件类型，列出被忽略的文件

### 素材类型识别

扫描完成后，统计各类型文件数量，确定素材类型：
- **文档为主**（PDF/MD/DOC > 50%）：标准流程
- **代码为主**（代码文件 > 50%）：重点关注架构和模块关系
- **数据为主**（JSON/YAML/CSV > 50%）：重点关注数据结构和统计
- **已有分析**（HTML 文件）：提取已有分析内容作为素材

## 步骤 1：素材提取

对每个源文件执行两阶段提取。**不调用任何外部 skill，所有逻辑内嵌。**

### 阶段 1a：初稿提取

读取源文件全文后，使用 `references/prompts.md` 中的"素材提取 Prompt"提取关键信息。

### 阶段 1b：密度增强（1-2轮）

使用 `references/prompts.md` 中的"密度增强 Prompt"识别遗漏。

### 输出格式

每源文件一份**素材卡片**（≤600字）：

```markdown
## 素材卡片：{文件名}

- **类型**：{文档/代码/数据}
- **核心主题**：{一句话}
- **关键数据点**：
  1. {数据点1}（来源：{原文位置}）
  2. {数据点2}（来源：{原文位置}）
  ...
- **核心结论**：
  1. {结论1}
  2. {结论2}
  ...
- **关键术语**：
  - {术语1}：{定义}
  ...
- **因果关系**：
  - {因} → {果}
  ...
- **与其他素材的关系**：{引用/对比/演进}
- **可视化建议**：{适合画什么图}
```

### PDF 文件处理

PDF 文件用 Read 工具分页读取：
- 第一轮：读取前 5 页，提取标题、作者、摘要
- 后续轮：每次读取 20 页，直到读完
- 如果 PDF 是扫描件（无文字层），在素材卡片中标注 `[扫描件，无法提取文字]`，基于已有知识生成标注为 `[非原文内容]` 的补充信息

### 代码文件处理

对代码文件，提取：
- 模块/文件结构
- 类定义和继承关系
- 关键函数签名和功能
- 依赖关系（import）
- 配置和常量
- 注释中的关键说明

### 已有 HTML 分析报告处理

如果输入包含已有的 HTML 分析报告（如知识图谱分析），提取：
- 报告的主要章节和结论
- 关键数据和统计
- 已有的 SVG 图表（可直接复用或改造为解释性风格）

## 步骤 2：类比映射

**这是 plainreport 的核心差异化步骤。** deepreport 在此步做"结构规划"，但 plainreport 的结构固定为 9 节，无需规划。取而代之的是为每个核心技术概念生成日常类比。

使用 `references/prompts.md` 中的"类比映射 Prompt"，对素材卡片中识别的所有核心技术概念执行类比映射。

### 类比映射输出格式

```markdown
### 类比卡片：{概念名}

- **概念**：{技术概念名称}
- **日常类比**：{2-3句话，用"就像..."开头}
- **映射点**：
  - 类比中的 A = 技术中的 X
  - 类比中的 B = 技术中的 Y
  - ...
- **类比失效点**：{这个类比无法解释什么}
- **场景标签**：{如"公司管理"、"交通系统"、"厨房"}
```

### 类比一致性原则

- 同一报告中的类比尽量来自同一个"生活场景"（如都用"公司管理"或都用"交通系统"），保持阅读连贯性
- 如果不同概念适合不同场景，确保每个场景内部的类比是一致的
- 类比不能歪曲技术事实——类比中的因果关系必须与技术概念中的因果关系一致

## 步骤 3：内容生成

**核心原则：类比在前，定义在后；只说素材中有的，不编造、不外推。**

按 `references/section-schema.md` 中的固定 9 节结构逐章生成。

### 内容生成约束

使用 `references/prompts.md` 中的"类比优先内容约束"（9条规则）。

### 生成顺序

按章节顺序生成，每章节：
1. 先写正文内容（基于素材卡片 + 类比卡片整合）
2. 再画 SVG 图表（根据 `references/svg-guide.md` 中的模板）
3. 最后加表格和特殊组件

### SVG 图表生成

根据 `references/svg-guide.md` 中的 6 类解释性 SVG 模板生成。

### 通俗化原则

- 每个核心概念先用**类比**解释，再给精确定义
- 类比用日常生活场景（公司管理、微信群、开车、厨房、快递等）
- 技术术语首次出现时用括号附日常解释，如：EKF2（扩展卡尔曼滤波器，就像一个"数据整合大师"）
- 不使用代码片段、命令行示例
- 不使用数学公式，用流程类比代替
- 语气口语化，像在跟朋友聊天解释

## 步骤 4：事实验证（不可跳过）

**这是确保内容正确性的关键步骤。绝不跳过。**

对步骤 3 生成的每章节内容执行验证。使用 `references/prompts.md` 中的"事实验证 Prompt"。

### 验证规则

1. **数值验证**：所有数字必须与原文完全一致
2. **结论验证**：因果关系必须有原文支持
3. **图表验证**：SVG 中的标注数据必须与正文一致
4. **引用验证**：引用的名称、年份必须准确
5. **范围验证**：如果原文说"在某些情况下"，报告中不能说"总是"
6. **类比验证**：类比中的因果关系必须与原文中的因果关系一致，不能为了类比简单化而歪曲事实

### 验证后处理

- 删除所有 UNVERIFIED 和 CONTRADICTED 的内容
- 修正 PARTIALLY_VERIFIED 的内容
- 如果删除导致某段落空洞，用 `[原文未提供此方面信息]` 标注，不编造填充
- SVG 图表中的数据同步修正

## 步骤 5：组装输出

单文件 HTML，严格使用 `references/html-style.md` 中的样式系统。

### 导航栏生成规则

导航栏链接根据实际章节结构动态生成：
- 主章节：`<a href="#sN">N. 章节名</a>`
- 子章节（第 3 节的子节等）：`<a class="sub" href="#sN-M">N.M 子章节名</a>`
- 子章节链接缩进显示，字号略小

### 章节结构

### 输出规范

## 硬性约束（MANDATORY — 违反任何一条即视为输出不合格）

> 历史问题：之前的执行中，LLM 倾向于"自行设计"CSS、自创类名、使用深色主题、省略核心组件。
> 以下约束是为了防止这些问题再次发生。**每一条都是血的教训。**

### M1. CSS 必须原样粘贴，禁止自创

`references/html-style.md` 中的 CSS 是**固定模板**，必须完整粘贴到 `<style>` 标签中。

**禁止**：
- 禁止修改任何 CSS 变量值（颜色、字号、间距等）
- 禁止新增 CSS 类名（`.badge`、`.quote`、`.mono`、`.highlight`、`.icon` 等均不允许）
- 禁止替换为深色主题（`--bg` 必须为 `#fafbfc`，不得改为 `#0f172a` 等深色值）
- 禁止省略任何 CSS 规则

**自检**：生成 HTML 后，对比 `references/html-style.md` 中的 CSS，确认 100% 一致。

### M2. JS 必须原样粘贴

`references/html-style.md` 中的 JS（导航栏高亮 + 平滑滚动）必须完整粘贴到 `<script>` 标签中。**禁止**修改或省略。

### M3. 9 节结构固定不变

必须严格按以下 9 节生成，章节标题和顺序不可更改：

| 节号 | id | 标题格式 | 必含组件 |
|------|-----|---------|---------|
| 1 | s1 | `{主题} 是什么？` | `.analogy` + `.stat-row` + `.card-grid` |
| 2 | s2 | `支持哪些能力？` | `.analogy` + `.card-grid` + `.table-wrap` + `.key-point` |
| 3 | s3 | `{主题} 怎么做的？` | `.analogy` + `.subsection` + `.svg-wrap`（≥1个SVG） |
| 4 | s4 | `举例说明` | `.example-box` + `.step` + `.svg-wrap`（≥1个SVG） |
| 5 | s5 | `效果怎么样？` | `.card-grid` + `.key-point` |
| 6 | s6 | `解决了哪些痛点？` | `.table-wrap`（3列：痛点/没有时/有了后） |
| 7 | s7 | `目前还有哪些问题？` | `.pros-cons`（`.con` + `.pro`） |
| 8 | s8 | `主要应用场景` | `.scenario-grid` + `.scenario-card` + `.table-wrap` |
| 9 | s9 | `一图总结` | `.svg-wrap`（1个径向总结SVG，必需） |

**禁止**：增减节数、更改节标题、合并/拆分章节。

### M4. 核心特色组件必须使用

以下组件是 plainreport 的灵魂，**每份报告必须出现**：

- `.analogy`（类比块）：第 1-3 节至少各出现 1 次
- `.key-point`（关键要点块）：第 2、5 节至少各出现 1 次
- `.stat-row` + `.stat-box`（统计数字行）：第 1 节必须出现
- `.example-box` + `.step`（示例步骤）：第 4 节必须出现
- `.pros-cons`（优缺点双栏）：第 7 节必须出现
